## 1. TL;DR

RAG Knowledge Chatbot is a serverless retrieval-augmented chatbot that answers questions about Jimmy's engineering background or the AWS Well-Architected Framework, with answers grounded in retrieved chunks across both knowledge bases and generated by Bedrock Claude Haiku 4.5. The retrieval layer is custom — no Bedrock Knowledge Bases, no managed vector service — with a single combined index in S3 and cosine similarity running inside the query Lambda. Stack: vanilla HTML/CSS/JS frontend on S3 + CloudFront, two Python 3.12 Lambdas (ingest + query) behind a REST API, Bedrock Titan Embeddings v2 + Claude Haiku 4.5 via cross-region inference profile, CloudFormation-managed, $20/month hard cap via AWS Budgets.

## 3. Architecture

The vanilla HTML/CSS/JS frontend at `frontend/index.html` is served from the `frontend/*` prefix of a shared S3 bucket fronted by CloudFront. When a user submits a question, the frontend posts JSON `{question}` to `POST /query` on REST API `uiauqskgv0` stage `dev`. The query Lambda (`rag-chatbot-query-dev`) handles it: embed the question via Bedrock Titan Embeddings v2 (1536-dim), cosine-search the in-memory 61 MB index for top-5 chunks across both knowledge bases, build an Anthropic Messages API request with the retrieved context, invoke Bedrock Haiku 4.5 via cross-region inference profile, and return the answer plus the retrieved chunks (with relevance scores and a `source_kb` tag per chunk) in a single response.

Ingestion is offline — a separate `rag-chatbot-ingest-dev` Lambda or `scripts/ingest_bulk.py` (for long-form corpus loads that exceed Lambda's 15-minute ceiling) reads documents from `data/documents/` and `data/well-architected/`, chunks them (175 words with 20-word overlap), embeds each chunk via Titan v2, and writes the combined `documents/index.json` (61 MB) to the same shared bucket under a non-public prefix. The index loads into a module-level `_index_cache` on first invocation and is kept warm by a 5-minute EventBridge ping — the warmup branch calls `_load_index()` so every container has the index ready before its first real query.

## 5. Build history

### Phase 1 — Initial scaffold + retrieval tuning + multi-KB (2026-04-14 → 2026-04-17)

CloudFormation stack `rag-knowledge-chatbot` provisioned the entire backend in one template: shared S3 bucket, two Lambdas (ingest + query), REST API, IAM roles, CloudWatch alarms, SNS topic, EventBridge warmup rule, AWS Budgets. First working end-to-end query against the Jimmy knowledge base by `v0.7-observability`. Retrieval tuning iterated chunk size from 500 words down to 175 with 20-word overlap, lifting retrieval scores on open-ended queries from under 0.30 to above 0.40 (`v0.8-integration` → `v0.9-polish`). Phase 8 (per the original phase numbering) added the AWS Well-Architected Framework PDFs as a second knowledge base combined into the same index with `source_kb` tagging (`v1.0-multikb`).

### Phase 2 — Multi-cloud experimentation + warmup hardening (2026-04-18 → 2026-04-19)

This phase explored multi-cloud generation as a portfolio signal. Nebius AI Studio was added as Provider B alongside Bedrock; the frontend exposed a provider toggle so the demo could route generation to either backend. The Nebius "fast tier" was parked when no `-fast` variant existed for Llama 3.3-70B. SambaNova was then swapped in for Nebius as Provider B (`4be78af`, tag `v1.1-sambanova`). Warmup hardening landed in the same window: the warmup branch was extended to also call `_load_index()` and pre-populate the module-level `_index_cache`, eliminating the ~6-second S3 load penalty on the first real query per container (first-touch cold dropped from ~8.3 s to ~4.7 s end-to-end). Mobile responsive layout shipped alongside (Phase 8.5); iOS Safari input zoom prevented.

### Phase 3 — Bedrock-only rework (2026-04-27, tag `v1.2-bedrock-only`)

The multi-cloud experiment was reversed. The SambaNova generation path was stripped from the query Lambda (`636891c`), the provider toggle was removed from the frontend (`430d8ab`), and the docs were updated (`694dc09`). Honest framing: multi-cloud was tried, didn't survive the simplification pass — single provider won on grounds of one fewer rate-limit to handle, one fewer timeout to tune, one fewer account to maintain, and one less surface area for failure modes that would distract from the RAG architecture itself. The planning doc, originally `PROJECT_PLANNING_MULTICLOUD.md`, was renamed to reflect the post-pivot scope (`d1b2955`).

### Phase 4 — CI/CD added, then the prefix incident (2026-05-04 → 2026-05-08)

The project's most recruiter-relevant moment, framed as a meta-learning incident.

**2026-05-04, commit `e0d91a9`** — frontend CI/CD added. Push-triggered workflow with a `frontend/**` path filter, syncing the local `frontend/` directory to S3 then invalidating CloudFront. Workflow committed without a post-deploy verification step.

**2026-05-04 → 2026-05-08 — the live URL was broken for three days.** The bucket policy authorizes public-read on the `frontend/*` prefix only. The new workflow synced to bucket root (`s3://…-dev/`) rather than `s3://…-dev/frontend/`. CloudFront's `DefaultRootObject = frontend/index.html` looked for the asset under that prefix; the new sync had placed `index.html` at root, leaving the prefix path empty. Console status and CloudFront invalidation completion both reported success while the live URL returned 403. The bug was discovered during the subdomain wiring work on 2026-05-08.

**2026-05-08, commit `6fe9c2d`** — deploy-side fix. The workflow's sync target was changed from `s3://…-dev/` to `s3://…-dev/frontend/`. One-line workflow change. No CloudFront config touched, no bucket policy touched — the problem was where the artifacts landed, not how CloudFront served them.

The incident produced a permanent rule added to global tooling guidelines (CloudFront/S3 Verification Rule), applied across the portfolio.

### Phase 5 — Subdomain + portfolio integration (2026-05-08 → 2026-05-09)

Subdomain `rag.jimmyhubbard2.cc` mapped via cPanel CNAME → CloudFront (`a630285`). CloudFormation template reconciled to deployed state (`077807a`) — drift between local template and live infrastructure cleaned up. Portfolio link updated to `projects.jimmyhubbard2.cc` (`4fe2458`). End of active build cycle.

### Operational gotchas

Sharp edges to know when touching this code:

1. **Never add `--delete` to the S3 sync.** The workflow comment documents why — would wipe `documents/index.json` (the 61 MB irreplaceable vector index), `lambda/` deployment packages, and `cloudtrail/` audit logs. ## 7. Key decisions

### 1. Custom retrieval over Bedrock Knowledge Bases

The project deliberately avoided AWS's managed RAG offering (Bedrock Knowledge Bases) in favor of a custom retrieval layer where chunks live as a single 61 MB JSON index in S3 and cosine similarity runs inside the query Lambda. Three concrete reasons drove the choice:

- **Cost** — managed KBs charge per-document and per-query overhead that wouldn't have justified itself at $5-10/month demo volume; the custom path runs on S3 storage + Lambda compute, both effectively free at this scale.
- **Control** — the chunker, embedder, and similarity logic are explicit code paths; chunk size, overlap, and top-K can be tuned without going through a managed-service abstraction.
- **Simplicity for two combined KBs** — a managed KB would have meant one index per knowledge base plus a reconciliation layer; the custom approach is one cosine pass plus sort by score, with a `source_kb` tag per chunk driving the UI differentiation (orange badges for Jimmy's background, blue for AWS Well-Architected).

Evidence the custom path was actually tuned, not just chosen and forgotten: chunk size tuned from 500 words down to 175 with 20-word overlap, lifting retrieval scores on open-ended queries from under 0.30 to above 0.40; top-K raised from 3 to 5 to fix incomplete-answer cases where enumeration chunks scored 0.40+ but got outranked by narrative chunks sharing query vocabulary. Trade-off: no managed search analytics, no built-in query rewriting, no approximate-nearest-neighbor — but at 2,027 chunks the linear cosine scan costs ~250 ms per query, well within budget.

### 2. Warmup with index cache priming (dual-purpose)

EventBridge fires the query Lambda every 5 minutes with `{"warmup": true}` payload. The obvious purpose — keep the container warm so the next user query doesn't pay a cold start — is well-trodden. The second purpose, added after diagnosing real failure modes in production, is what makes this distinctive: the warmup branch calls `_load_index()` to pre-populate the module-level `_index_cache`. Every container spawned by a warmup ping has the 61 MB index ready before the first real user query, eliminating the ~6 s S3-load penalty that previously hit every container's first touch. Measured impact: first-touch cold dropped from ~8.3 s end-to-end (~6 s S3 load + ~2 s Bedrock) to ~4.7 s (cache hit + ~4 s Bedrock). Warmup runs ~$0.03/month. The two-function warmup isn't standard cargo-cult Lambda warmup — it's specifically tuned against the S3-load failure mode this architecture creates.

### 3. Shared bucket with prefix-scoped public-read policy

The single S3 bucket `rag-chatbot-603509861186-dev` serves four roles under prefix segregation: `frontend/*` (static site, publicly readable via bucket policy `PublicReadFrontend`), `documents/*` (RAG corpus + 61 MB index, not public), `lambda/*` (Lambda deployment zips, not public), `cloudtrail/*` (audit logs from `rag-chatbot-trail-dev`, not public). The safety boundary is the bucket policy's `Resource: …/frontend/*` scope — Public Access Block must stay off (all four settings) for the policy itself to take effect, so the policy itself is what gates public exposure.

This is the legacy pre-OAC pattern that the other six portfolio projects migrated away from in early May 2026. The trade-off accepted here: one bucket consolidating all project artifacts, easier to reason about as a unit, vs. four separate buckets that would each support the OAC + REST origin pattern. Splitting into four buckets to enable OAC would require rewriting the deploy workflow (multi-target sync), the Lambda code (multi-bucket reads), and the CloudFront origin config (four origins plus path-based routing). For demo traffic at $5-10/month, the migration cost isn't yet justified. Tracked as Future Enhancement E2 with the bucket-restructure cost called out explicitly.

### 4. Observability shipped from day one — operational alarms + cost budgets

The project ships both operational alarms (Lambda error rate > 5%, p95 duration > 12 s) and AWS Budgets (alert at $15 and $18 against a $20 cap). The two work together — alarms catch reliability issues, budgets catch cost issues. Both alarms route to the project SNS topic; both budgets alert on email. Current state: alarms OK, spend $5.79 (well under both budget thresholds).

The pattern was shaped by the four-day prefix-incident outage (Phase 4). If alarms had been wired against CloudFront error rate, the broken live URL would have been detected within minutes instead of three days. The Lambda-level alarms shipped from day one don't cover the CloudFront case directly, but the discipline of "alarm what you care about, don't wait for a user to report it" was established here.

## 8. Future enhancements

### E1 — Bump GitHub Actions to v6 majors (priority: medium)

`.github/workflows/deploy.yml` pins `actions/checkout@v4` and `aws-actions/configure-aws-credentials@v4`. These v4 actions run on Node.js 20, which is deprecated on the GitHub Actions runner.

- **2026-06-02** — Actions are forced to run on Node.js 24 by default. v4 actions whose internal JS is not Node-24-compatible may behave differently from this date.
- **2026-09-16** — Node.js 20 is removed from the runner entirely. v4 actions will fail to start from this date.

rag-chatbot joins ntcip-simulator, traffic-dashboard, and linux-ops on the v4 holdout list. Recommended bump before 2026-06-02. Fix is a one-line edit per action.

### E2 — OAC migration with bucket restructure (priority: low)

The current shared-bucket + S3-website + public-read pattern (Decision 3) is the legacy pre-OAC posture that the rest of the portfolio migrated away from in May 2026. Migration here is non-trivial because it requires splitting the four prefix-roles into separate buckets — `rag-chatbot-frontend-{account}`, `rag-chatbot-documents-{account}`, `rag-chatbot-lambda-{account}`, `rag-chatbot-cloudtrail-{account}` — each able to support `PublicAccessBlock` all-on with appropriate access patterns. CloudFront origin would be reconfigured to REST endpoint + OAC. Deploy workflow would target the new frontend bucket. Lambda code would update its `S3_BUCKET` env var to point at the new documents bucket. Bucket restructure is the larger task; the OAC change itself is one-line per stack. Estimated effort 4-6 hours plus a data-migration window. Priority low because the current trade-off is well-documented and the cost-saving is zero at portfolio scale.

### E3 — Grant `portfolio-user` CLI observability reads (priority: low)

Standard portfolio-wide carry-over. `cloudwatch:GetMetricStatistics` and `ce:GetCostAndUsage` return AccessDenied for the `portfolio-user` IAM principal. Applies portfolio-wide.

### E4 — End-to-end test in CI (priority: medium)

CI today deploys the frontend but doesn't verify the live POST → 200 → JSON shape loop. A synthetic question plus a real POST plus a check on response structure (answer field present, retrieved-chunks array present with score + source_kb tag per chunk) would catch regressions in retrieval, generation, and the API integration. Cost: one Titan embed plus one Haiku call per CI run, well under the $20 budget.

### E5 — Move Lambda deploy into CI (priority: low-medium)

Lambda deploys are currently manual — `lambda-query.zip` at repo root suggests one-shot uploads. Adding a backend deploy step to GitHub Actions, gated by a diff-guard on `backend/**` paths, would close the manual-deploy gap and keep changes under audit trail. Needs broader IAM permissions for the GitHub Actions credentials (CloudFormation, Lambda Update, IAM).
